# 仓库导览与提交规则

本仓库只服务于 Dinomaly 课程复现。当前是服务器前准备阶段，测试通过不等于真实实验完成。先阅读根目录 README 的实验矩阵与运行命令。

## 一、已经上传的内容

| 位置 | 分类与用途 | 保留理由 |
|---|---|---|
| `run.py` | 程序入口 | 数据校验、训练、评测和汇总的统一命令 |
| `course/model.py` | 方法装配 | 复用上游模块，按 B/F/A1/A2/A3 装配注意力、瓶颈、监督和损失 |
| `course/train.py` | 训练管理 | 固定更新步数、日志、优化器状态、随机数与数据位置恢复、最终权重导出 |
| `course/evaluate.py` | 统一评测 | 固定掩码和后处理协议，保存逐类指标、逐样本预测和来源 |
| `course/summarize.py` | 结果汇总 | 检查比较条件，计算类别宏平均、跨种子均值/标准差与配对差值 |
| `course/data.py` | 数据检查与读取 | 保留 15 类原划分，按文件名配对掩码 |
| `course/runtime.py` | 复现记录 | 配置校验、随机种子、文件哈希、环境和源码指纹 |
| `configs/*.json` | 五组实验配置 | 明确实际训练参数与机制差异；字段解释见下表 |
| `configs/run-matrix.csv` | 九次运行清单 | 计划清单，`not_started` 不代表已经训练 |
| `tests/test_workflow.py` | 软件验证 | 随机权重/合成数据检查，不能作为论文结果 |
| `vendor/dinomaly/` | 固定上游实现与参考 | 保留已有方法来源和原始实现，未修改第三方代码 |
| `vendor/SOURCE.json` | 上游来源清单 | 固定提交及每个保留文件的 SHA256 |
| `requirements-*.txt` | 环境复现 | 区分 CPU 实测版本和 Linux CUDA 候选版本 |
| `README.md`、`docs/` | 使用与验收说明 | 数据获取、运行、续训、评测、版本状态及发布规则 |
| `LICENSE`、`NOTICE.md`、`CITATION.cff` | 授权与引用 | 保留原作者归属，声明复现而非原创方法 |
| `.gitignore`、`.gitattributes` | Git 管理规则 | 排除大文件/敏感内容，并保持上游文件字节与哈希一致 |
| `results/README.md` | 结果目录说明 | 当前只有状态说明，没有真实结果表 |

**必要性边界：** 以上主体是运行、复现或交付所需。`vendor/dinomaly/` 为保留上游目录结构而包含了一些当前主路径未使用的辅助模块，不能声称每个上游文件都是训练必需。正式 GPU 路径验证后，再以独立 Git 提交精简，先验证干净副本仍可运行，不提前删除潜在依赖。原始 CPU 测试日志仅作本地记录，不继续公开跟踪；仓库保留简洁的验收说明和可重跑测试。

## 二、配置字段注解

JSON 不支持注释，因此在这里集中解释，避免加入非法注释导致配置无法读取。

| 字段 | 含义 |
|---|---|
| `variant` | 实验编号 B、F、A1、A2、A3 |
| `encoder` | `base` 默认；`small` 仅作为全组统一降级方案，均带 register tokens |
| `image_size`、`crop_size` | 缩放边长、中心裁剪边长 |
| `batch_size`、`steps` | 每个物理 batch 图片数、优化器更新步数 |
| `warmup_steps`、`lr`、`final_lr` | 学习率预热步数、基准学习率、余弦调度终值 |
| `weight_decay`、`grad_clip` | 优化器权重衰减、梯度范数裁剪上限 |
| `noise_dropout` | 官方瓶颈 MLP 的 Dropout 概率 |
| `attention` | `linear` 为 LinearAttention2，`softmax` 为普通注意力 |
| `supervision` | `group` 为两组融合监督，`dense` 为八层逐层监督 |
| `loss` | `loose` 为官方宽松余弦梯度机制，`cosine` 为普通全局余弦损失 |
| `save_every` | 滚动 checkpoint 保存间隔，以更新步为单位 |
| `eval_size`、`max_ratio` | 评测图尺寸、图像分数使用的最高异常像素比例 |
| `workers` | 数据加载进程数，不是 GPU 数量 |

种子、设备、数据路径、预训练文件和输出目录通过命令行传入；真实使用配置会随每次运行另存。不因命名相同就混合不同训练预算或评测协议。

## 三、后续何时上传

采用**本地持续管理、阶段完成后同步 GitHub**，不把每个临时文件都上传，也不等整个大作业结束才一次性上传。

| 阶段 | 检查后上传 | 保持本地或单独备份 |
|---|---|---|
| 代码修改 | 实际使用的代码、配置、必要测试与说明 | 临时调试脚本、缓存、失败运行文件 |
| 服务器验证 | 实际验证后的环境清单、简洁验证记录、必要适配 | Python 环境、安装缓存、服务器凭据 |
| 正式实验 | 核验后的逐类/汇总 CSV、相对路径来源清单、必要日志摘要 | 数据集、全部逐步日志和逐样本数组、优化器断点 |
| 结果分析 | 论文使用的必要图表、分析代码、可追溯说明 | 重复图、试画图、无用中间产物 |
| 权重发布 | 经重载核验的基线、完整方法与消融推理权重放 Releases，并给出 SHA256 | `last.pt` 等续训状态另做两地备份 |
| 最终交付 | 完善 README、引用、代码版本与结果/权重对应清单 | 含个人信息的论文 Word/PDF 默认不公开 |

`runs/` 内自动生成的来源文件可能带本地路径、用户名或环境信息；公开时只导出所需字段，检查后提交。不要直接把整个运行目录移进 `results/`。没有真实结果前，不上传虚构数字、占位提升幅度或预设结论。

## 四、如何使用 Git

- `main` 保存经过适当检查的阶段版本；较大或有风险的修改使用短期分支，小范围文档修改可直接提交到 main。
- 提交前查看差异，按具体文件暂存，检查是否包含数据、大文件或凭据；做与改动相关的检查，再写清楚本次目的。
- 一个完整改动一个提交，不把临时调试状态当作正式版本。重要阶段可建立标签；最终训练必须记录实际代码提交与源码指纹。
- 本机 Git 与 GitHub 插件各有自己的认证；首次上传通过插件完成，后续可由插件同步，或在本机完成认证后正常 `git push`。
- 插件创建提交后重新拉取并核对内容，避免本地与远端各自修改同一文件而失去同步。保留历史，不强制覆盖远端。

示例（仅展示常规本机 Git 操作，实际文件按本次修改选择）：

```bash
git status
git diff
git add README.md docs/REPOSITORY_GUIDE.md
git diff --cached --check
git diff --cached
git commit -m "docs: explain repository layout and publishing policy"
git push
```
